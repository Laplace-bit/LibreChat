# Pi agent runtime migration

## Decision

Integrate Pi inside the LibreChat server as an alternate agent execution engine. Keep the existing desktop renderers, HTTP/SSE contracts, authorization, MongoDB conversation and message records, and `GenerationJobManager` as the product-owned boundaries. Create one Pi session per admitted generation and use an in-memory Pi session manager. LibreChat remains authoritative for conversation history; a Pi session is temporary execution state and is never the durable transcript.

The existing Agent engine stays enabled and remains the default until parity, concurrency, recovery, security, and performance acceptance passes. Rollout is selected by server-side configuration for an agent. Switching engines must not rewrite stored conversations.

It requires Node.js `>=22.19.0`, compatible with the repository's CI Node.js `24.22.1` baseline. Its npm tarball SHA-512 is `sha512-Z41LpZ3yYHSC/UUps6Mr39UMFPwH8elhJBG9DY1P7kuzsE5qSK/6eMj2EHzO5evJRQWLbKSqUMw+4nCNtIyiQg==`; its license is MIT.

The committed dependency inventory at [`pi-agent-dependencies.json`](./pi-agent-dependencies.json) is generated by `node scripts/verify-pi-dependencies.mjs`. It follows the Pi SDK's production dependency closure in `package-lock.json` and resolves license fields from installed package metadata when the lock entry omits them. The current closure contains 161 package instances with no unknown or unlicensed entries: 88 MIT, 38 Apache-2.0, 13 BSD-3-Clause, 14 ISC, 6 BlueOak-1.0.0, 1 Unlicense, and 1 0BSD. This records package metadata; production rollout still requires the deployment's dependency and license policy review.

Adding Pi changed 26 existing root dependency resolutions in `package-lock.json`, primarily AWS/Smithy, Google GenAI, and YAML packages, in addition to the Pi dependency closure. Some are exact Pi provider dependencies and some are npm hoisting/range resolutions. This is an explicit compatibility review item for legacy provider behavior; the lockfile has not been trimmed by deleting required Pi transitive dependencies.

Lockfile regeneration also hoisted four pre-existing client dependencies from `client/node_modules` to the root: Sandpack `2.19.10` to `2.20.0`, MCP UI `5.7.0` to `5.17.3`, `babel-plugin-transform-import-meta` `2.3.2` to `2.3.3`, and `react-is` `17.0.2` to `18.3.1`. These are semver-compatible with the client declarations but are unrelated to Pi; Web and desktop builds are required before treating this lockfile as accepted.

The SDK is currently constructed with an explicit resource loader, host-supplied tools, settings, and in-memory session manager. Each generation must receive a fresh model/runtime binding. Pi sees a synthetic working-directory label that does not point to a host workspace; built-in filesystem tools, resource discovery, local credentials, and extension loading are disabled. The adapter does not expose Pi's mutable session object. Do not load project-local Pi extensions. Admin-approved extensions are trusted server code and must be installed by deployment administrators.

The dependency inventory is recorded, but production rollout remains blocked on compatibility testing for the changed shared provider dependencies and deployment-policy review of the dependency set. Adding the SDK is not approval to enable Pi for production agents.

## Execution and ownership

```text
HTTP request
  -> existing auth, tenant and agent admission
  -> GenerationJobManager claims generation ownership
  -> selected runtime receives validated request context
     -> legacy AgentClient, or
     -> Pi SDK session with explicit provider, prompt, tools and resources
  -> runtime events are translated to the existing event handlers
  -> existing job manager owns pause, resume, abort, replay and terminal state
  -> existing persistence writes LibreChat messages and artifacts
```

The Pi adapter owns only the Pi session and translation of Pi model/tool events into host events. It does not own admission, durable messages, approvals, authorization, retries after process loss, or terminal state. Session disposal follows generation settlement and abort. A resumed generation reconstructs a new Pi session from the persisted LibreChat transcript and validated resume context.

## Integration boundary

Do not replace the HTTP routes or `GenerationJobManager`: the main chat route, resume route, and OpenAI-compatible endpoints perform distinct host admission and lifecycle work. The main chat path constructs `AgentClient` in `api/server/services/Endpoints/agents/initialize.js`; `AgentClient` currently calls `createRun` in `api/server/controllers/agents/client.js`. Direct run construction also exists in `api/server/controllers/agents/openai.js`, `api/server/controllers/agents/responses.js`, `api/server/controllers/assistants/chatV1.js`, and `api/server/controllers/assistants/chatV2.js`.

Two tempting shortcuts do not meet the migration target. Replacing `createRun` with a Pi-shaped object would also have to reproduce `graphRunnable.getState`, graph checkpoint access, activity/title generation, interrupt detection, resume, and the host callback event contract. Wrapping Pi as only a LangGraph chat model would preserve the graph but leave LangGraph as the agent loop, so it would not replace the requested runtime. The selected direction is a shared execution-engine seam behind the existing host initialization and job admission: legacy and Pi engines must feed the same persistence, SSE, authorization, auditing, cancellation, and terminal-state boundaries. That seam is not implemented yet; do not route any request to Pi until its contract covers all current callers and resume modes.

Code and command execution must use the existing authorized Code API. Do not enable Pi's local `bash`, `read`, `edit`, `write`, `grep`, or `find` tools in the server process. If the Code API is missing or unavailable, those operations fail closed. MCP and business tools are added individually through host-owned handlers after the same authorization checks used by the current path.

The isolated Pi session factory is implemented and tested as a foundation only. It loads the SDK without filesystem/extension discovery, requires a request-scoped model binding, accepts only host-supplied tools, keeps session state in memory, can prefill ordered messages into Pi's in-memory `SessionManager`, checks cancellation, and performs idempotent cleanup. The structured history converter preserves server-formatted user, assistant, tool-call and tool-result messages plus authorized inline images; it leaves the current user message as the prompt and rejects unsupported content, remote images, unmatched tool calls and provider-specific signatures. A separate translator maps Pi text and reasoning deltas into the host's message-creation, message-delta, reasoning-delta, and step-closure events; it does not map tools, usage, citations, attachments or errors. A local fake OpenAI SSE provider verifies structured history and image prompt delivery, host-tool exchange, text/reasoning event mapping through LibreChat's content aggregator, active provider cancellation, and eight isolated concurrent sessions. These tests do not exercise LibreChat's provider authorization or `ToolService`, and neither adapter is wired into `AgentClient` or the OpenAI/Responses paths. Provider policy mapping, durable history/recovery, persisted approvals/resume, and capability parity remain unimplemented. The legacy runtime remains the only execution path until those gaps and the rollout gates are closed.

Pi-specific interactive terminal behavior is outside the product scope. Any Pi capability not represented by a row above must be reviewed and added to this matrix before exposure.

## Rollout gates

1. Record legacy throughput, p50/p95 latency, error rate, memory and CPU for the target deployment shape.
2. Run the same scenarios against Pi with the engine selector restricted to internal agents.
3. Pass feature parity, access-control, sandbox, cancellation, resume, multi-replica, and stale-owner tests.
4. Meet or exceed the legacy concurrency and latency baseline without increasing cross-tenant or duplicate side effects.
5. Expand by controlled agent allowlist. Keep the legacy engine as the immediate fallback until history continuation and rollback are verified.
6. Remove the legacy engine only in a separately reviewed change after production evidence confirms the migration gates.

## Known constraints

- The repository's current default Compose stack does not prove that an external Code API is installed or safely configured. Pi code execution remains unavailable until the deployment's Code API isolation and per-user authorization are verified.
- The upstream Pi SDK currently supports in-memory sessions, custom resources and custom tools, but its provider and event contracts differ from LibreChat's. Provider mapping and event translation are required; the SDK does not replace host authorization or durable job recovery.
- Performance and concurrency targets are relative to a measured deployment baseline. No absolute capacity claim is made before those measurements exist.
