# Pi agent runtime migration

## Decision

Use Pi as the only Agent execution engine on `feature/pi-agent-runtime`. Keep the existing desktop and Web chat entry points, HTTP/SSE contracts, authorization, MongoDB conversation and message records, and `GenerationJobManager` as product-owned boundaries. Create one Pi session per admitted generation and use an in-memory Pi session manager. LibreChat remains authoritative for conversation history; a Pi session is temporary execution state and is never the durable transcript.

Every new supported Agent chat generation is pinned to Pi before execution. Pi errors and unsupported features fail closed; they never dispatch to the previous Agent engine. Existing transcripts remain LibreChat data. A paused generation without a validated Pi continuation cannot be resumed by switching engines. Generic non-Agent jobs retain their existing job metadata semantics.

## Pinned Pi package

Use `@earendil-works/pi-coding-agent` version `1.4.0` as the initial SDK candidate, pinned to upstream tag [`v1.4.0`](https://github.com/earendil-works/pi/tree/v1.4.0) at commit `4a080252f06caf63a525d7873c5d94d3c23887e0`. It requires Node.js `>=22.19.0`, compatible with the repository's CI Node.js `24.22.1` baseline. Its npm tarball SHA-512 is `sha512-Z41LpZ3yYHSC/UUps6Mr39UMFPwH8elhJBG9DY1P7kuzsE5qSK/6eMj2EHzO5evJRQWLbKSqUMw+4nCNtIyiQg==`; its license is MIT.

The committed dependency inventory at [`pi-agent-dependencies.json`](./pi-agent-dependencies.json) is generated by `node scripts/verify-pi-dependencies.mjs`. It follows the Pi SDK's production dependency closure in `package-lock.json` and resolves license fields from installed package metadata when the lock entry omits them. The current closure contains 161 package instances with no unknown or unlicensed entries: 88 MIT, 38 Apache-2.0, 13 BSD-3-Clause, 14 ISC, 6 BlueOak-1.0.0, 1 Unlicense, and 1 0BSD. This records package metadata; production rollout still requires the deployment's dependency and license policy review.

Adding Pi changed 26 existing root dependency resolutions in `package-lock.json`, primarily AWS/Smithy, Google GenAI, and YAML packages, in addition to the Pi dependency closure. Some are exact Pi provider dependencies and some are npm hoisting/range resolutions. The affected provider implementations require regression testing; the lockfile has not been trimmed by deleting required Pi transitive dependencies.

Lockfile regeneration also hoisted four pre-existing client dependencies from `client/node_modules` to the root: Sandpack `2.19.10` to `2.20.0`, MCP UI `5.7.0` to `5.17.3`, `babel-plugin-transform-import-meta` `2.3.2` to `2.3.3`, and `react-is` `17.0.2` to `18.3.1`. These are semver-compatible with the client declarations but are unrelated to Pi; Web and desktop builds are required before treating this lockfile as accepted.

The SDK is currently constructed with an explicit resource loader, host-supplied tools, settings, and in-memory session manager. Each generation must receive a fresh model/runtime binding. Pi sees a synthetic working-directory label that does not point to a host workspace; built-in filesystem tools, resource discovery, local credentials, and extension loading are disabled. The adapter does not expose Pi's mutable session object. Pi extension loading is disabled, so administrators cannot install Pi extensions through this adapter.

Pi's built-in automatic compaction remains disabled because its checkpoint would live only in the temporary Pi session and its usage would bypass LibreChat accounting. Ordinary turns first apply the existing host tool-result caps to a provider-only history projection. When whole-message pruning is required and automatic summarization is enabled, the host validates an exact contiguous prefix/suffix split, keeps the configured recent-turn window and latest user message, then runs a separate tool-free Pi summary phase under the same GenerationJob and abort signal. The summary uses the original old-message prefix, is persisted through the existing summary events with a durable retained-message coverage ID, and only then can the primary Pi turn start with that summary and retained tail. LibreChat history is not rewritten. Ambiguous tool boundaries, missing source IDs, unsupported summary model settings, an over-budget summary input, failed/empty summaries, or cancellation stop before the primary turn. Same-provider/model automatic summarization and the persisted formatter coverage path have focused tests; production-provider behavior, alternate summary models, and full rollout parity remain open.

The dependency inventory is recorded. Production deployment still requires regression testing for changed shared provider dependencies and deployment-policy review of the dependency set.

## Execution and ownership

```text
HTTP request
  -> existing auth, tenant and agent admission
  -> GenerationJobManager claims generation ownership
  -> Pi SDK session with explicit provider, prompt, tools and resources
  -> runtime events are translated to the existing event handlers
  -> existing job manager owns abort, replay, approval and terminal state
  -> existing persistence writes LibreChat messages and artifacts
```

The Pi adapter owns the Pi session and translation of Pi model/tool events into host events. It does not own admission, durable messages, authorization, retries after process loss, or terminal state. Session disposal follows generation settlement and abort. A fresh Pi generation reconstructs its temporary session from the persisted LibreChat transcript. Pi marks the host-owned execution progress record when its isolated session is created. The marker is monotonic for the client and separate from the Pi continuation envelope and job status. Failed-turn trace persistence reads this marker rather than inferring Pi execution from a completed outcome. Supported Pi tool approvals persist a server-only continuation envelope beside the existing pending action and resume through the existing approval CAS. Resume validates one unfinished host tool call against that envelope and the current host-built definition. MCP and Action approvals bind the current schema; Actions also bind the name, description, and OAuth flag. Code API approvals carry a bounded server-only session snapshot and opaque target binding.

Every new Agent generation records the immutable Pi SDK identity in existing job metadata. The in-memory and Redis job stores carry the identity through the job facade, and Redis retains malformed values so the runtime boundary rejects them instead of treating them as absent. Generic non-Agent jobs leave this field unset; an old or unknown Agent engine identity is unsupported. Resume reads the stored identity before claiming an approval, validates the continuation against the exact pending action, unfinished host run step and aggregated tool-call content, then uses the existing single-winner approval CAS. It never re-evaluates configuration or silently changes engines. Old paused Agent jobs without a Pi continuation fail closed.

## Integration boundary

### Provider credential authorization

Pi provider bindings are minted inside the existing provider initializers only after they resolve the credential source, model, API variant and transport. Supported candidates are built-in OpenAI Responses; explicitly selected OpenAI Chat Completions for catalogued non-reasoning models; canonical Anthropic Messages; direct Google Gemini with a server-admin key; and canonical Azure OpenAI Responses v1 for catalogued Azure models. OpenAI and Anthropic require server-admin credentials. Google Vertex, Bedrock, user-provided credentials, custom destinations, unsupported proxy/header/query configurations, provider remapping and unlisted model/API variants remain unavailable to Pi. Azure Pi requests use the v1 Responses API even when the existing Azure host client configures a separate preview query for its own transport. Provider coverage is a vetted subset, not automatic OpenAI compatibility.

`initializeAgent()` currently copies the resolved `llmConfig` into the in-memory agent's `model_parameters`, and that configuration may contain `apiKey`. Its shape does not retain credential provenance, so Pi must never treat `agent.model_parameters` or `llmConfig` as authorization evidence. The Pi caller receives only a request-scoped binding factory created by the trusted initializer; the Pi adapter does not add credentials to generation metadata, SSE events, Pi history, logs, or persisted transcript data. The resolver keeps the credential in a server-side closure, validates the final model, API variant, and supported generation parameters, and only then exposes a Pi model/runtime pair.

The main chat route and resume route preserve their host admission and lifecycle work. The main chat path constructs `AgentClient` in `api/server/services/Endpoints/agents/initialize.js`. `AgentClient` sends turns to the Pi-only `createAgentRuntimeDispatcher` in `packages/api/src/agents/runtime/dispatcher.ts`, while retaining history and permission checks, event handling, approval persistence, job state, and finalization. OpenAI-compatible Agent Chat Completions and Agent Responses controllers retain their endpoint request and response contracts and call the same Pi dispatcher through `remotePi.js`; Chat Completions projects host events to its SSE format, while Responses also supports validated caller-tool handoff. Provider Assistants routes use separate provider APIs and do not select the Agent execution runtime.

The runtime dispatcher exposes Pi-only `executeTurn` and `resumeTurn` commands. It validates the job's persisted Pi identity before calling the Pi generation dispatcher and returns its typed outcome without creating `this.run`. The dispatcher does not own authorization, job state, approvals, or finalization. There is no Legacy Agent execution command or fallback.

Pi remains a narrow execution path, not a replacement `AgentRun` or a Pi-shaped graph. It consumes the server-formatted transcript, uses the exact authorized request-scoped OpenAI binding, and sends translated text, reasoning, tool-step, and token-usage events through existing host handlers. It does not publish SSE directly or own generation state. This path covers one exact root agent with no callable tools, or with the reviewed host `file_search`, `web_search`, `calculator`, managed stateless Code API `bash_tool`/`read_file`, compatible foreground MCP tools, and OpenAPI Actions whose current authorized definitions use the bounded flat scalar schema subset below. Actions and MCP calls use the existing host `ON_TOOL_EXECUTE` handler. Pi evaluates the host `PreToolUse` policy before tool dispatch. Interactive approval uses the existing action payload and resume route. MCP continuations bind the current tool name and schema; Action continuations bind the current name, description, OAuth flag, and schema. Both fail closed on resume if the current host-built definition changed or disappeared. Code API approval revalidates the resolved target before executing. Per-agent grants and an attached Code API environment remain ineligible. Unsupported lifecycle features remain rejected; this is a development slice, not product parity.

Code and command execution must use the existing authorized Code API. Do not enable Pi's local `bash`, `read`, `edit`, `write`, `grep`, or `find` tools in the server process. If the Code API is missing or unavailable, those operations fail closed. Foreground MCP tools and OpenAPI Actions use the same host-owned handler and current authorization checks as other tools. Pi receives only the authorized tool name, bounded schema and call arguments; MCP and Action credentials stay in the initialized server context. The Action adapter accepts only the schema subset below; nested objects, arrays, references, unions, resources, unsupported schema keywords, and unsupported result artifacts remain unavailable. Action host execution continues to own OAuth login/refresh, SSRF protection, HTTP timeout, and ActionService error handling.

#### Pi OpenAPI Action schema subset

| Area               | Accepted shape                                                                                                                 | Boundary                                                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| Root               | `type: object`; required `properties` object; optional `description` and `required`; `additionalProperties` omitted or `false` | Schema JSON ≤64 KiB; nesting depth ≤8; at most 64 properties and required keys                                                   |
| Properties         | Flat `string`, `number`, `integer`, or `boolean`; optional `description` and scalar `enum`                                     | Property names ≤256 characters; descriptions ≤4,096 characters; enums contain 1–128 unique values                                |
| String bounds      | `minLength` and/or `maxLength`                                                                                                 | Safe integers from 0 to 65,536; minimum must not exceed maximum                                                                  |
| Numeric bounds     | `minimum` and/or `maximum`                                                                                                     | Finite numbers; integer fields require safe integer bounds; minimum must not exceed maximum                                      |
| Call arguments     | Exact JSON object with declared keys only; all required keys present and every value checked against type, enum and bounds     | JSON ≤64 KiB; at most 64 fields; unsupported objects, accessors, prototypes, non-finite numbers, and extra keys fail closed      |
| Definition binding | Fingerprint includes exact Action tool name, description, OAuth flag and raw parameters after canonical object-key ordering    | Approval resume uses the newly built server-side Action definitions; a same-name definition with changed fingerprint is rejected |

The adapter rejects nested objects, arrays, nullable and union types, `$ref`, `allOf`/`anyOf`/`oneOf`, `pattern`, `format`, `default`, and every unrecognized keyword. OpenAPI Actions whose request bodies use objects, arrays, file uploads, or other unsupported schemas fail closed on this branch. ActionService currently returns JSON-serialized object responses as text; Pi does not add Action-specific attachment, binary, or structured artifact projection.

### Human approval and durable resume

Reuse `GenerationJobManager.approvals`, the existing `pendingAction` record, and the current `/resume` request contract as the only durable pause and claim mechanism. `ToolApprovalGrantStorage` is for remembered grants and is not a pending-action store. A Pi tool gate must decide whether to execute, reject, or pause before calling `ON_TOOL_EXECUTE`; an approval request must never reach the host tool handler before the resume claim succeeds.

When a Pi tool requires a decision, the dispatcher must return an explicit `paused` outcome distinct from user cancellation. It must stop the active Pi prompt and drain the per-generation event FIFO before the host stages the action. The existing request controller remains responsible for persisting the unfinished assistant message before releasing the pause barrier and exposing the action to the client.

The Pi adapter evaluates the host static approval policy, conversation-level remembered allows, and registered `PreToolUse` hooks before supported host tools reach the handler, including `bash_tool` and `read_file` on an eligible managed stateless endpoint. An `allow` reaches `ON_TOOL_EXECUTE`; a `deny` records a failed tool step without host side effects; hook-rewritten arguments are schema-validated again. An `ask` creates the existing pending-action payload. The approval pause drains the per-generation event FIFO, persists the unfinished assistant message, then atomically stores the pending action and versioned Pi continuation in the existing job. Multi-call batches are rejected before any per-call gate or host handler runs. The gate observes raw OpenAI Completions and Responses events before Pi normalizes tool calls; repeated call IDs, malformed indexes, and multiple Completions choices fail closed before the parser can merge them. Other APIs fail closed when the gate is enabled.

After the existing resume route revalidates user, tenant, agent, action identity, request fingerprint, expiration and decision, it verifies that the continuation still matches exactly one unfinished supported host step and its aggregated content. Code API continuations also require the persisted session snapshot and current opaque target binding. Only the `approvals.resolve()` CAS winner executes the approved host action. The host tool result is settled against the original step identity, appended to a newly converted Pi transcript, and passed to Pi's low-level continuation API without replaying another user prompt. Reject and respond decisions produce a safe tool result without invoking the host tool. The continuation envelope contains no credentials or Pi SDK session state; Code API continuations include only the bounded server-side Code API session snapshot and opaque target binding. Redis serialization, stale-action cleanup, approval resolution, expiration and terminal paths clear it with the corresponding action transition.

Pi 1.4.0 does not expose an `AgentSession` continuation method for a restored tool result. The adapter uses `Agent.continue()` after it validates the assistant tool call and following result. The host wrapper owns the operation promise, aborts the Pi agent, and waits for the promise before disposal. A retryable `agent_end` fails closed because this path does not run `AgentSession` retry or compaction handling or its settled callbacks. The route and controller still own finalization. Fake-provider tests cover continuation and cancellation. Crash-after-action recovery and full request-to-provider initial-turn integration remain open. Host automatic summarization has dispatcher and formatter tests; production-provider behavior and alternate summary-model routing remain unverified. Approval resume is covered by the cross-replica Redis integration.

The Pi session factory loads the SDK without filesystem or extension discovery. It requires a request-scoped model binding, accepts host-supplied tools, keeps session state in memory, prefills ordered messages into Pi's in-memory `SessionManager`, checks cancellation, and performs idempotent cleanup. The runtime dispatcher calls Pi only when the job pins that engine, the loaded graph has one root agent, and every callable tool has a reviewed adapter. Supported adapters include `file_search`, `web_search`, `calculator`, `set_memory`, `delete_memory`, `skill`, compatible foreground MCP tools, bounded-schema OpenAPI Actions, and `bash_tool`/`read_file` when the managed stateless Code API is eligible. Scheduled Agent turns use the existing server scheduler and GenerationJobManager lifecycle. Authenticated bound Event Actor deliveries without expectedAction use the durable-history strategy; ordinary tool-approval and ask-user pauses resume only after the server validates the Pi continuation and live history token. EventActor checkpoint/warm/cold restoration, expectedAction and detached completion remain unavailable. Authorized one-level foreground subagent calls use the parent GenerationJob; detached/background subagent runs, continued or edited responses, alternate automatic-summary providers/models, and attached Code API environments remain unsupported. Standard regeneration reloads the authorized persisted user message, preserves the old response, and creates a new response branch; manual and supported automatic summarization use host-owned summary events. Production scheduler deployment, restart recovery, cancellation races, idempotency and audit behavior still require verification. Ordinary queued text and inline-image steering is supported at turn end; immediate preemption remains unsupported. Host tool adapters require the existing host execution handler. Before dispatch, the route checks the server-formatted transcript through the host's final model-bound content-policy boundary and commits deferred private-text persistence. Pi converts supported text and inline-image history and sends text, reasoning, tool lifecycle, token usage, summary lifecycle, and context snapshots through existing handlers. One per-generation FIFO serializes streamed and direct tool events. The dispatcher waits for the context snapshot handler before calling the primary model, and the token-usage event carries the same host `runId`. The job manager and existing persistence path retain ownership of messages, SSE, cancellation, cleanup, and usage.

Pi titles use a host adapter because the installed `@librechat/agents` package does not export its internal title runnables. The adapter honors the configured title endpoint, model, prompt, prompt template, and completion, functions or structured title method. Immediate titles use the first user message. Final titles use the completed response. Both wait for private-text admission and record title usage through the current host path. The adapter does not add the per-agent Langfuse tracing handler used by `Run.generateTitle()`.

## Deployment verification gates

1. Record the target deployment's current Legacy throughput, p50/p95 latency, error rate, memory and CPU as the comparison baseline.
2. Run the same supported Agent workloads against Pi in that deployment shape.
3. Pass feature, permission, sandbox, cancellation, approval-resume, multi-replica and stale-owner recovery tests.
4. Meet the measured Legacy capacity and latency baseline without increasing cross-tenant access or duplicate side effects.
5. Verify rollback by redeploying the previous application release and confirming stored conversations remain readable. This branch has no in-process Legacy Agent fallback.

## Known constraints

- The repository's current default Compose stack does not prove that an external Code API is installed or safely configured. Pi code execution remains unavailable until the deployment's Code API isolation and per-user authorization are verified.
- The upstream Pi SDK currently supports in-memory sessions, custom resources and custom tools, but its provider and event contracts differ from LibreChat's. Provider mapping and event translation are required; the SDK does not replace host authorization or durable job recovery.
- Performance and concurrency targets are relative to a measured deployment baseline. No absolute capacity claim is made before those measurements exist.
