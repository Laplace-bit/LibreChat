# Pi agent runtime migration

## Decision

Integrate Pi inside the LibreChat server as an alternate agent execution engine. Keep the existing desktop renderers, HTTP/SSE contracts, authorization, MongoDB conversation and message records, and `GenerationJobManager` as the product-owned boundaries. Create one Pi session per admitted generation and use an in-memory Pi session manager. LibreChat remains authoritative for conversation history; a Pi session is temporary execution state and is never the durable transcript.

The existing Agent engine stays enabled and remains the default until parity, concurrency, recovery, security, and performance acceptance passes. Rollout is selected by server-side configuration for an agent. Switching engines must not rewrite stored conversations.

## Pinned Pi package

Use `@earendil-works/pi-coding-agent` version `1.4.0` as the initial SDK candidate, pinned to upstream tag [`v1.4.0`](https://github.com/earendil-works/pi/tree/v1.4.0) at commit `4a080252f06caf63a525d7873c5d94d3c23887e0`. It requires Node.js `>=22.19.0`, compatible with the repository's CI Node.js `24.22.1` baseline. Its npm tarball SHA-512 is `sha512-Z41LpZ3yYHSC/UUps6Mr39UMFPwH8elhJBG9DY1P7kuzsE5qSK/6eMj2EHzO5evJRQWLbKSqUMw+4nCNtIyiQg==`; its license is MIT.

The committed dependency inventory at [`pi-agent-dependencies.json`](./pi-agent-dependencies.json) is generated by `node scripts/verify-pi-dependencies.mjs`. It follows the Pi SDK's production dependency closure in `package-lock.json` and resolves license fields from installed package metadata when the lock entry omits them. The current closure contains 161 package instances with no unknown or unlicensed entries: 88 MIT, 38 Apache-2.0, 13 BSD-3-Clause, 14 ISC, 6 BlueOak-1.0.0, 1 Unlicense, and 1 0BSD. This records package metadata; production rollout still requires the deployment's dependency and license policy review.

Adding Pi changed 26 existing root dependency resolutions in `package-lock.json`, primarily AWS/Smithy, Google GenAI, and YAML packages, in addition to the Pi dependency closure. Some are exact Pi provider dependencies and some are npm hoisting/range resolutions. This is an explicit compatibility review item for legacy provider behavior; the lockfile has not been trimmed by deleting required Pi transitive dependencies.

Lockfile regeneration also hoisted four pre-existing client dependencies from `client/node_modules` to the root: Sandpack `2.19.10` to `2.20.0`, MCP UI `5.7.0` to `5.17.3`, `babel-plugin-transform-import-meta` `2.3.2` to `2.3.3`, and `react-is` `17.0.2` to `18.3.1`. These are semver-compatible with the client declarations but are unrelated to Pi; Web and desktop builds are required before treating this lockfile as accepted.

The SDK is currently constructed with an explicit resource loader, host-supplied tools, settings, and in-memory session manager. Each generation must receive a fresh model/runtime binding. Pi sees a synthetic working-directory label that does not point to a host workspace; built-in filesystem tools, resource discovery, local credentials, and extension loading are disabled. The adapter does not expose Pi's mutable session object. Do not load project-local Pi extensions. Admin-approved extensions are trusted server code and must be installed by deployment administrators.

The dependency inventory is recorded, but production rollout remains blocked on compatibility testing for the changed shared provider dependencies and deployment-policy review of the dependency set. Adding the SDK is not approval to enable Pi for production agents.

## Execution and ownership

```text
HTTP request
  -> existing auth, tenant and agent admission
  -> GenerationJobManager claims generation ownership
  -> selected runtime receives validated request context
     -> legacy AgentClient, or
     -> Pi SDK session with explicit provider, prompt, tools and resources
  -> runtime events are translated to the existing event handlers
  -> existing job manager owns abort, replay and terminal state; Legacy and supported Pi approvals use its pause/resume flow
  -> existing persistence writes LibreChat messages and artifacts
```

The Pi adapter owns only the Pi session and translation of Pi model/tool events into host events. It does not own admission, durable messages, authorization, retries after process loss, or terminal state. Session disposal follows generation settlement and abort. A fresh Pi generation reconstructs its temporary session from the persisted LibreChat transcript. Both engines publish a host-owned runtime progress record: Legacy marks execution started when its real `AgentRun` is assigned, and Pi marks it when its isolated host session has been created. The marker is monotonic for the client and separate from the Legacy graph handle, Pi continuation envelope, and job status. Failed-turn trace persistence reads this shared marker instead of inferring Pi execution from a completed outcome. Supported Pi tool approvals persist a server-only continuation envelope beside the existing pending action and resume through the existing approval CAS. Resume validates one unfinished host tool call against that envelope and the current host-built definition. MCP and Action approvals bind the current schema; Actions also bind the name, description, and OAuth flag. Code API approvals carry a bounded server-only session snapshot and opaque target binding.

Every new generation records an immutable `agentRuntime` identity in the existing job metadata. The server config schema has an operator-only `endpoints.agents.runtime.piAgentIds` allowlist, defaulting to empty; tenant and user config cannot change it. Other agents explicitly select `legacy`; other generation creation defaults to `legacy`; older jobs with no identity also resolve to `legacy`. The in-memory and Redis job stores carry the identity through the job facade, and Redis retains malformed values so the runtime boundary can reject them instead of treating them as absent. Resume reads that persisted identity before claiming an approval or schedule slot, validates the continuation against the exact pending action, unfinished host run step and aggregated tool-call content, then uses the existing single-winner approval CAS. Resume never re-evaluates current configuration or silently changes engines. The allowlist must remain empty outside controlled testing until the feature, concurrency, recovery, security and performance gates below pass. A rolling deployment must not select Pi until every server replica understands and enforces the persisted identity and continuation envelope.

## Integration boundary

### Provider credential authorization

The Pi provider binding is limited to the built-in `openAI` endpoint with a server-admin `OPENAI_API_KEY` and the canonical OpenAI destination. It is minted inside `initializeOpenAI()` after that function resolves the credential source and transport. Responses is available when selected by the resolved host configuration. Chat Completions is available only when both the request model parameters and resolved host configuration explicitly select `useResponsesApi: false`, and only for catalogued non-reasoning models. User-provided keys or URLs, Azure, custom endpoints, reverse proxies, provider remapping, custom headers, reasoning on Completions, and unsupported API variants remain unavailable to Pi.

`initializeAgent()` currently copies the resolved `llmConfig` into the in-memory agent's `model_parameters`, and that configuration may contain `apiKey`. Its shape does not retain credential provenance, so Pi must never treat `agent.model_parameters` or `llmConfig` as authorization evidence. The Pi caller receives only a request-scoped binding factory created by the trusted initializer; the Pi adapter does not add credentials to generation metadata, SSE events, Pi history, logs, or persisted transcript data. The resolver keeps the credential in a server-side closure, validates the final model, API variant, and supported generation parameters, and only then exposes a Pi model/runtime pair.

Do not replace the HTTP routes or `GenerationJobManager`. The main chat route, resume route, and OpenAI-compatible endpoints perform distinct host admission and lifecycle work. The main chat path constructs `AgentClient` in `api/server/services/Endpoints/agents/initialize.js`. `AgentClient` sends turns to `createAgentRuntimeDispatcher` in `packages/api/src/agents/runtime/dispatcher.ts`, while retaining admission, history and permission checks, event handling, approval persistence, job state, and finalization. Pi is not wired into direct run construction in `api/server/controllers/agents/openai.js`, `api/server/controllers/agents/responses.js`, `api/server/controllers/assistants/chatV1.js`, or `api/server/controllers/assistants/chatV2.js`; those entry points retain their Legacy compatibility guards.

The runtime dispatcher exposes `executeTurn` and `resumeTurn` with engine-specific command and result types. It validates the job's persisted runtime selection before calling an engine. Legacy creates the existing `AgentRun`, waits for checkpoint pruning, and calls `processStream` or `resume`. Pi calls the Pi generation dispatcher and returns its typed outcome without creating `this.run`. The dispatcher does not own authorization, job state, approvals, or finalization. Engine failures do not fall back to Legacy.

Pi remains a narrow execution path, not a replacement `AgentRun` or a Pi-shaped graph. It consumes the server-formatted transcript, uses the exact authorized request-scoped OpenAI binding, and sends translated text, reasoning, tool-step, and token-usage events through existing host handlers. It does not publish SSE directly or own generation state. This path covers one exact root agent with no callable tools, or with the reviewed host `file_search`, `web_search`, `calculator`, managed stateless Code API `bash_tool`/`read_file`, compatible foreground MCP tools, and OpenAPI Actions whose current authorized definitions use the bounded flat scalar schema subset below. Actions and MCP calls use the existing host `ON_TOOL_EXECUTE` handler. Pi evaluates the host `PreToolUse` policy before tool dispatch. Interactive approval uses the existing action payload and resume route. MCP continuations bind the current tool name and schema; Action continuations bind the current name, description, OAuth flag, and schema. Both fail closed on resume if the current host-built definition changed or disappeared. Code API approval revalidates the resolved target before executing. Per-agent grants and an attached Code API environment remain ineligible. Unsupported lifecycle features remain rejected; this is a development slice, not product parity.

Code and command execution must use the existing authorized Code API. Do not enable Pi's local `bash`, `read`, `edit`, `write`, `grep`, or `find` tools in the server process. If the Code API is missing or unavailable, those operations fail closed. Foreground MCP tools and OpenAPI Actions use the same host-owned handler and current authorization checks as other tools. Pi receives only the authorized tool name, bounded schema and call arguments; MCP and Action credentials stay in the initialized server context. The Action adapter accepts only the schema subset below; nested objects, arrays, references, unions, resources, unsupported schema keywords, and unsupported result artifacts remain unavailable. Action host execution continues to own OAuth login/refresh, SSRF protection, HTTP timeout, and ActionService error handling.

#### Pi OpenAPI Action schema subset

| Area               | Accepted shape                                                                                                                 | Boundary                                                                                                                         |
| ------------------ | ------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------- |
| Root               | `type: object`; required `properties` object; optional `description` and `required`; `additionalProperties` omitted or `false` | Schema JSON ≤64 KiB; nesting depth ≤8; at most 64 properties and required keys                                                   |
| Properties         | Flat `string`, `number`, `integer`, or `boolean`; optional `description` and scalar `enum`                                     | Property names ≤256 characters; descriptions ≤4,096 characters; enums contain 1–128 unique values                                |
| String bounds      | `minLength` and/or `maxLength`                                                                                                 | Safe integers from 0 to 65,536; minimum must not exceed maximum                                                                  |
| Numeric bounds     | `minimum` and/or `maximum`                                                                                                     | Finite numbers; integer fields require safe integer bounds; minimum must not exceed maximum                                      |
| Call arguments     | Exact JSON object with declared keys only; all required keys present and every value checked against type, enum and bounds     | JSON ≤64 KiB; at most 64 fields; unsupported objects, accessors, prototypes, non-finite numbers, and extra keys fail closed      |
| Definition binding | Fingerprint includes exact Action tool name, description, OAuth flag and raw parameters after canonical object-key ordering    | Approval resume uses the newly built server-side Action definitions; a same-name definition with changed fingerprint is rejected |

The adapter rejects nested objects, arrays, nullable and union types, `$ref`, `allOf`/`anyOf`/`oneOf`, `pattern`, `format`, `default`, and every unrecognized keyword. OpenAPI Actions whose request bodies use objects, arrays, file uploads, or other unsupported schemas remain on the Legacy engine. ActionService currently returns JSON-serialized object responses as text; Pi does not add Action-specific attachment, binary, or structured artifact projection.

### Human approval and durable resume

Reuse `GenerationJobManager.approvals`, the existing `pendingAction` record, and the current `/resume` request contract as the only durable pause and claim mechanism. `ToolApprovalGrantStorage` is for remembered grants and is not a pending-action store. A Pi tool gate must decide whether to execute, reject, or pause before calling `ON_TOOL_EXECUTE`; an approval request must never reach the host tool handler before the resume claim succeeds.

When a Pi tool requires a decision, the dispatcher must return an explicit `paused` outcome distinct from user cancellation. It must stop the active Pi prompt and drain the per-generation event FIFO before the host stages the action. The existing request controller remains responsible for persisting the unfinished assistant message before releasing the pause barrier and exposing the action to the client.

The Pi adapter evaluates the host static approval policy, conversation-level remembered allows, and registered `PreToolUse` hooks before supported host tools reach the handler, including `bash_tool` and `read_file` on an eligible managed stateless endpoint. An `allow` reaches `ON_TOOL_EXECUTE`; a `deny` records a failed tool step without host side effects; hook-rewritten arguments are schema-validated again. An `ask` creates the existing pending-action payload. The approval pause drains the per-generation event FIFO, persists the unfinished assistant message, then atomically stores the pending action and versioned Pi continuation in the existing job. Multi-call batches are rejected before any per-call gate or host handler runs. The gate observes raw OpenAI Completions and Responses events before Pi normalizes tool calls; repeated call IDs, malformed indexes, and multiple Completions choices fail closed before the parser can merge them. Other APIs fail closed when the gate is enabled.

After the existing resume route revalidates user, tenant, agent, action identity, request fingerprint, expiration and decision, it verifies that the continuation still matches exactly one unfinished supported host step and its aggregated content. Code API continuations also require the persisted session snapshot and current opaque target binding. Only the `approvals.resolve()` CAS winner executes the approved host action. The host tool result is settled against the original step identity, appended to a newly converted Pi transcript, and passed to Pi's low-level continuation API without replaying another user prompt. Reject and respond decisions produce a safe tool result without invoking the host tool. The continuation envelope contains no credentials or Pi SDK session state; Code API continuations include only the bounded server-side Code API session snapshot and opaque target binding. Redis serialization, stale-action cleanup, approval resolution, expiration and terminal paths clear it with the corresponding action transition.

Pi 1.4.0 does not expose an `AgentSession` continuation method for a restored tool result. The adapter uses `Agent.continue()` after it validates the assistant tool call and following result. The host wrapper owns the operation promise, aborts the Pi agent, and waits for the promise before disposal. A retryable `agent_end` fails closed because this path does not run `AgentSession` retry or compaction handling or its settled callbacks. The route and controller still own finalization. Fake-provider tests cover continuation and cancellation. Crash-after-action recovery, full request-to-provider initial-turn integration, and Pi automatic compaction remain unverified; approval resume is covered by the cross-replica Redis integration.

The Pi session factory loads the SDK without filesystem or extension discovery. It requires a request-scoped model binding, accepts host-supplied tools, keeps session state in memory, prefills ordered messages into Pi's in-memory `SessionManager`, checks cancellation, and performs idempotent cleanup. The runtime dispatcher calls Pi only when the job pins that engine, the loaded graph has one root agent, and every callable tool has a reviewed adapter. Supported adapters include `file_search`, `web_search`, `calculator`, `set_memory`, `delete_memory`, `skill`, compatible foreground MCP tools, bounded-schema OpenAPI Actions, and `bash_tool`/`read_file` when the managed stateless Code API is eligible. Event Actor, scheduled or background work, compaction, regeneration, steering, and attached Code API environments remain unsupported. Host tool adapters require the existing host execution handler. Before dispatch, the route checks the server-formatted transcript through the host's final model-bound content-policy boundary and commits deferred private-text persistence. Pi converts supported text and inline-image history and sends text, reasoning, tool lifecycle, token usage, and context snapshots through existing handlers. One per-generation FIFO serializes streamed and direct tool events. The dispatcher waits for the context snapshot handler before calling the model, and the token-usage event carries the same host `runId`. The job manager and existing persistence path retain ownership of messages, SSE, cancellation, cleanup, and usage.

Pi titles use a host adapter because the installed `@librechat/agents` package does not export its internal title runnables. The adapter honors the configured title endpoint, model, prompt, prompt template, and completion, functions or structured title method. Immediate titles use the first user message. Final titles use the completed response. Both wait for private-text admission and record title usage through the current host path. The adapter does not add the per-agent Langfuse tracing handler used by `Run.generateTitle()`.

The local fake OpenAI SSE integration verifies structured history, inline-image prompts, host-tool exchange, text and reasoning events, context-snapshot ordering, provider cancellation, and restored tool-result continuation without prompt replay. Another session test runs eight isolated sessions concurrently. A separate generation integration runs two jobs through `GenerationJobManager` and local SSE providers. It checks tool, usage, run, terminal-event, and abort isolation. Focused bridge, executor, and runtime-dispatcher tests cover event ordering, drain-before-completion, cancellation, disposal, error precedence, and Legacy/Pi execution and resume routes. AgentClient tests verify pinned Pi dispatch without constructing `AgentRun`, host usage routing, prompt projection, final content-policy checks, and private-text persistence before execution. The host-tool slice supports `file_search`, `web_search`, `calculator`, `set_memory`, `delete_memory`, `skill`, managed stateless Code API `bash_tool`/`read_file`, authorized foreground MCP tools, and current authorized OpenAPI Actions that fit the bounded flat scalar schema. The adapters validate arguments, use host authorization hooks, serialize run-local file and session references, and persist approval continuations. MCP continuations bind the schema fingerprint. Action continuations bind the current host definition and revalidate edited arguments before model or host execution. Controller tests verify Action dispatch through `ON_TOOL_EXECUTE`, reject a changed Action definition after approval, and a loopback integration covers a real no-OAuth Action HTTP request through the existing host service. OAuth authorization/refresh/callback and production SSRF enforcement remain unverified. A local-provider web-search integration checks that the model citation anchor and host search artifact use the same turn. Persisted citation reload and Web/Desktop rendering remain open. The Code API loopback integration runs Pi bash through the host `createBashExecutionTool`, verifies the minted JWT signature and user/tenant/role claims, rejects untrusted arguments before the request, and confirms the `/v1/exec` call; the real Code API verifier and isolation controls remain unverified. The Redis cross-replica integration runs the actual `/resume` route on replica B for an approval staged on replica A and verifies one CAS winner, one host side effect, resumed provider execution, and terminal cleanup. Other product tools, provider-native tools, and Pi local shell/filesystem tools remain unavailable. Per-agent title tracing, attachments beyond supported inline images, production Code API verifier/tenant ACL/artifact/isolation round-trip, Code API profiles beyond managed stateless, business connectors outside the Action adapter, MCP resources and non-text artifacts, administrator-approved extensions, subagents, a complete fake-provider ask-user answer/resume flow, scheduled or background work, other provider and API surfaces, same-session and stale-owner races, crash/restart recovery, and measured load and performance baselines remain open. Keep the operator allowlist empty and Legacy as the default until those gaps pass review and verification.

The provider binding supports built-in OpenAI Responses and explicitly selected Chat Completions with an administrator API key, canonical destination, supported model parameters, and the timeout/proxy dispatcher selected for the legacy client. `reasoning_effort` maps only to levels supported by the selected Pi Responses model; Completions only accepts catalogued non-reasoning models. LibreChat `none` is rejected for Responses because Pi has no equivalent. The binding transfers through a `WeakMap` to the exact initialized agent; no enumerable credential or callable field enters agent, graph, or job state. User keys and URLs, Azure, reverse proxies, custom headers, custom query/fetch behavior, provider-native tools, and unsupported model parameters remain ineligible. Local HTTP tests verify canonical routing to both API paths, credential isolation, proxy and timeout behavior, the Responses reasoning shape, and a Completions request without reasoning fields. The host dispatch path routes provider-reported token usage through existing usage accounting; cost and context-budget parity still require end-to-end verification.

Pi-specific interactive terminal behavior is outside the product scope. Any Pi capability not represented by a row above must be reviewed and added to this matrix before exposure.

## Rollout gates

1. Record legacy throughput, p50/p95 latency, error rate, memory and CPU for the target deployment shape.
2. Run the same scenarios against Pi with the engine selector restricted to internal agents.
3. Pass feature parity, access-control, sandbox, cancellation, resume, multi-replica, and stale-owner tests.
4. Meet or exceed the legacy concurrency and latency baseline without increasing cross-tenant or duplicate side effects.
5. Expand by controlled agent allowlist. Keep the legacy engine as the immediate fallback until history continuation and rollback are verified.
6. Remove the legacy engine only in a separately reviewed change after production evidence confirms the migration gates.

## Known constraints

- The repository's current default Compose stack does not prove that an external Code API is installed or safely configured. Pi code execution remains unavailable until the deployment's Code API isolation and per-user authorization are verified.
- The upstream Pi SDK currently supports in-memory sessions, custom resources and custom tools, but its provider and event contracts differ from LibreChat's. Provider mapping and event translation are required; the SDK does not replace host authorization or durable job recovery.
- Performance and concurrency targets are relative to a measured deployment baseline. No absolute capacity claim is made before those measurements exist.
