# Pi agent runtime migration

## Decision

Integrate Pi inside the LibreChat server as an alternate agent execution engine. Keep the existing desktop renderers, HTTP/SSE contracts, authorization, MongoDB conversation and message records, and `GenerationJobManager` as the product-owned boundaries. Create one Pi session per admitted generation and use an in-memory Pi session manager. LibreChat remains authoritative for conversation history; a Pi session is temporary execution state and is never the durable transcript.

The existing Agent engine stays enabled and remains the default until parity, concurrency, recovery, security, and performance acceptance passes. Rollout is selected by server-side configuration for an agent. Switching engines must not rewrite stored conversations.

## Pinned Pi package

Use `@earendil-works/pi-coding-agent` version `1.4.0` as the initial SDK candidate, pinned to upstream tag [`v1.4.0`](https://github.com/earendil-works/pi/tree/v1.4.0) at commit `4a080252f06caf63a525d7873c5d94d3c23887e0`. It requires Node.js `>=22.19.0`, compatible with the repository's CI Node.js `24.22.1` baseline. Its npm tarball SHA-512 is `sha512-Z41LpZ3yYHSC/UUps6Mr39UMFPwH8elhJBG9DY1P7kuzsE5qSK/6eMj2EHzO5evJRQWLbKSqUMw+4nCNtIyiQg==`; its license is MIT.

The committed dependency inventory at [`pi-agent-dependencies.json`](./pi-agent-dependencies.json) is generated by `node scripts/verify-pi-dependencies.mjs`. It follows the Pi SDK's production dependency closure in `package-lock.json` and resolves license fields from installed package metadata when the lock entry omits them. The current closure contains 161 package instances with no unknown or unlicensed entries: 88 MIT, 38 Apache-2.0, 13 BSD-3-Clause, 14 ISC, 6 BlueOak-1.0.0, 1 Unlicense, and 1 0BSD. This records package metadata; production rollout still requires the deployment's dependency and license policy review.

Adding Pi changed 26 existing root dependency resolutions in `package-lock.json`, primarily AWS/Smithy, Google GenAI, and YAML packages, in addition to the Pi dependency closure. Some are exact Pi provider dependencies and some are npm hoisting/range resolutions. This is an explicit compatibility review item for legacy provider behavior; the lockfile has not been trimmed by deleting required Pi transitive dependencies.

Lockfile regeneration also hoisted four pre-existing client dependencies from `client/node_modules` to the root: Sandpack `2.19.10` to `2.20.0`, MCP UI `5.7.0` to `5.17.3`, `babel-plugin-transform-import-meta` `2.3.2` to `2.3.3`, and `react-is` `17.0.2` to `18.3.1`. These are semver-compatible with the client declarations but are unrelated to Pi; Web and desktop builds are required before treating this lockfile as accepted.

The SDK is currently constructed with an explicit resource loader, host-supplied tools, settings, and in-memory session manager. Each generation must receive a fresh model/runtime binding. Pi sees a synthetic working-directory label that does not point to a host workspace; built-in filesystem tools, resource discovery, local credentials, and extension loading are disabled. The adapter does not expose Pi's mutable session object. Do not load project-local Pi extensions. Admin-approved extensions are trusted server code and must be installed by deployment administrators.

The dependency inventory is recorded, but production rollout remains blocked on compatibility testing for the changed shared provider dependencies and deployment-policy review of the dependency set. Adding the SDK is not approval to enable Pi for production agents.

## Execution and ownership

```text
HTTP request
  -> existing auth, tenant and agent admission
  -> GenerationJobManager claims generation ownership
  -> selected runtime receives validated request context
     -> legacy AgentClient, or
     -> Pi SDK session with explicit provider, prompt, tools and resources
  -> runtime events are translated to the existing event handlers
  -> existing job manager owns abort, replay and terminal state; Legacy also owns its pause/resume flow
  -> existing persistence writes LibreChat messages and artifacts
```

The Pi adapter owns only the Pi session and translation of Pi model/tool events into host events. It does not own admission, durable messages, approvals, authorization, retries after process loss, or terminal state. Session disposal follows generation settlement and abort. A fresh Pi generation reconstructs its temporary session from the persisted LibreChat transcript. A paused Pi generation cannot yet resume; the resume route rejects it before claiming approval or schedule state.

Every new generation records an immutable `agentRuntime` identity in the existing job metadata. The server config schema has an operator-only `endpoints.agents.runtime.piAgentIds` allowlist, defaulting to empty; tenant and user config cannot change it. Other agents explicitly select `legacy`; other generation creation defaults to `legacy`; older jobs with no identity also resolve to `legacy`. The in-memory and Redis job stores carry the identity through the job facade, and Redis retains malformed values so the runtime boundary can reject them instead of treating them as absent. Resume reads that persisted identity before claiming an approval or schedule slot. Pi jobs fail closed on resume until a durable Pi resume adapter exists; resume never re-evaluates current configuration or silently changes engines. The allowlist now reaches a deliberately narrow Pi text-generation path, but must remain empty outside controlled testing until the feature, concurrency, recovery, and deployment gates below pass. A rolling deployment must not select Pi until every server replica understands and enforces the persisted identity.

## Integration boundary

### Provider credential authorization

The first Pi provider binding is limited to the built-in `openAI` endpoint with a server-admin `OPENAI_API_KEY` and the canonical OpenAI destination. It must be minted inside `initializeOpenAI()` after that function has resolved the credential source and transport. User-provided keys or URLs, Azure, custom endpoints, reverse proxies, provider remapping, custom headers, and unsupported API variants remain unavailable to Pi until a dedicated adapter proves equivalent routing and authorization.

`initializeAgent()` currently copies the resolved `llmConfig` into the in-memory agent's `model_parameters`, and that configuration may contain `apiKey`. Its shape does not retain credential provenance, so Pi must never treat `agent.model_parameters` or `llmConfig` as authorization evidence. The Pi caller receives only a request-scoped binding factory created by the trusted initializer; the Pi adapter does not add credentials to generation metadata, SSE events, Pi history, logs, or persisted transcript data. The resolver keeps the credential in a server-side closure, validates the final model, API variant, and supported generation parameters, and only then exposes a Pi model/runtime pair.

Do not replace the HTTP routes or `GenerationJobManager`: the main chat route, resume route, and OpenAI-compatible endpoints perform distinct host admission and lifecycle work. The main chat path constructs `AgentClient` in `api/server/services/Endpoints/agents/initialize.js`; `AgentClient` selects either `createRun` or the Pi dispatcher in `api/server/controllers/agents/client.js`. Pi is not wired into direct run construction in `api/server/controllers/agents/openai.js`, `api/server/controllers/agents/responses.js`, `api/server/controllers/assistants/chatV1.js`, or `api/server/controllers/assistants/chatV2.js`; those entry points retain their Legacy compatibility guards.

Pi dispatch is currently a narrow branch inside the existing `AgentClient` lifecycle, not a replacement `AgentRun` or a Pi-shaped graph. It consumes the server-formatted transcript, uses the exact authorized request-scoped OpenAI binding, and sends translated text, reasoning, tool-step, and token-usage events through existing host handlers. It does not create `this.run`, publish SSE directly, or own generation state. This seam covers one exact root agent with no callable tools, or with only `file_search` when its validated schema and host `ON_TOOL_EXECUTE` handler are available. Unsupported lifecycle features remain rejected; this is a development slice, not product parity.

Code and command execution must use the existing authorized Code API. Do not enable Pi's local `bash`, `read`, `edit`, `write`, `grep`, or `find` tools in the server process. If the Code API is missing or unavailable, those operations fail closed. MCP and business tools are added individually through host-owned handlers after the same authorization checks used by the current path.

### Human approval and durable resume

Reuse `GenerationJobManager.approvals`, the existing `pendingAction` record, and the current `/resume` request contract as the only durable pause and claim mechanism. `ToolApprovalGrantStorage` is for remembered grants and is not a pending-action store. A Pi tool gate must decide whether to execute, reject, or pause before calling `ON_TOOL_EXECUTE`; an approval request must never reach the host tool handler before the resume claim succeeds.

When a Pi tool requires a decision, the dispatcher must return an explicit `paused` outcome distinct from user cancellation. It must stop the active Pi prompt and drain the per-generation event FIFO before the host stages the action. The existing request controller remains responsible for persisting the unfinished assistant message before releasing the pause barrier and exposing the action to the client.

After the existing resume route revalidates user, tenant, agent, action identity, request fingerprint, expiration and decision, only the `approvals.resolve()` CAS winner may construct a new in-memory Pi session. The Pi resume adapter should project the authoritative LibreChat transcript plus the verified `pendingAction` into the expected tool call and result, then continue generation through a narrow SDK continuation API. Do not persist Pi SDK sessions or credentials in job metadata. Until this adapter and its races are implemented and tested, Pi resume remains rejected before any action or schedule claim.

The Pi session factory loads the SDK without filesystem or extension discovery, requires a request-scoped model binding, accepts only host-supplied tools, keeps session state in memory, can prefill ordered messages into Pi's in-memory `SessionManager`, checks cancellation, and performs idempotent cleanup. The main AgentClient route calls the one-turn dispatcher only when the job's pinned runtime is Pi and the loaded graph is a single root with either no callable tools or only the supported `file_search` tool, and no skills, Event Actor, scheduled or background work, compaction, regeneration, or steering. The file-search adapter is created only when the existing host execution handler is available. Before dispatch, the route checks the server-formatted transcript through the host's final model-bound content-policy boundary and commits deferred private-text persistence. It then converts supported text and inline-image history. The Pi model binding comes from the exact initialized Agent identity and authorized OpenAI configuration. Pi text, reasoning, tool lifecycle, token usage and the context snapshot go through existing handlers. One per-generation FIFO serializes streamed and direct tool events. The dispatcher waits for the snapshot handler before it calls the model, and the token usage event carries the same host runId. The job manager and current persistence path retain ownership of messages, SSE, cancellation, cleanup and usage.

Pi titles use a host adapter because the installed `@librechat/agents` package does not export its internal title runnables. The adapter honors the configured title endpoint, model, prompt, prompt template, and completion, functions or structured title method. Immediate titles use the first user message. Final titles use the completed response. Both wait for private-text admission and record title usage through the current host path. The adapter does not add the per-agent Langfuse tracing handler used by `Run.generateTitle()`.

The local fake OpenAI SSE integration verifies structured history and inline-image prompt delivery, host-tool exchange at the isolated-session layer, text and reasoning mapping through LibreChat's content aggregator, context-snapshot ordering, active provider cancellation, and eight concurrent isolated sessions. Focused bridge and executor tests verify asynchronous handler ordering, drain-before-completion, cancellation, disposal, and error precedence. AgentClient tests verify that a supported pinned Pi turn reaches the dispatcher without constructing `AgentRun`, routes primary usage through the host handler, includes the same agent instructions, dynamic context, and LibreChat summary in the Pi system prompt, checks the final formatted input before dispatch, and admits protected private-text persistence before execution. Static memory, knowledge retrieval, and connector guidance already folded into the host's additional instructions are now passed through that prompt projection. The first ToolService slice supports only host-authorized `file_search`; it has strict schema/argument tests and a typed batch adapter to the current handler. A Pi host-tool integration test verifies run/thread/user/agent/call/step ownership and waits for the injected artifact callback before resolving the tool batch; the real controller callback remains covered by its artifact tests. Pi-specific persisted citation and Web/Desktop rendering checks remain open. Other tools, provider-native tools, and Pi local shell/filesystem tools remain unavailable. Per-agent title tracing, attachments beyond supported inline images, Code API execution, callable MCP and business tools, inline memory tools, skills, administrator-approved extensions, subagents, approvals, durable resume, scheduled or background work, other provider and API surfaces, multi-replica races, and measured load and performance baselines remain open. Keep the operator allowlist empty in normal deployments and keep Legacy as the default until those gaps pass review and verification.

The first provider binding is limited to built-in OpenAI Responses with an administrator API key, canonical destination, supported model parameters and headers, and the timeout/proxy dispatcher selected for the legacy client. It transfers through a `WeakMap` to the exact initialized agent; no enumerable credential or callable field enters agent, graph, or job state. User keys and URLs, Azure, reverse proxies, custom headers, custom query/fetch behavior, provider-native tools, and unsupported model parameters remain ineligible. Real local stream tests verify credential isolation, proxy and timeout behavior without external network access. The host dispatch path now routes provider-reported token usage through existing usage accounting; cost and context-budget parity still require end-to-end verification.

Pi-specific interactive terminal behavior is outside the product scope. Any Pi capability not represented by a row above must be reviewed and added to this matrix before exposure.

## Rollout gates

1. Record legacy throughput, p50/p95 latency, error rate, memory and CPU for the target deployment shape.
2. Run the same scenarios against Pi with the engine selector restricted to internal agents.
3. Pass feature parity, access-control, sandbox, cancellation, resume, multi-replica, and stale-owner tests.
4. Meet or exceed the legacy concurrency and latency baseline without increasing cross-tenant or duplicate side effects.
5. Expand by controlled agent allowlist. Keep the legacy engine as the immediate fallback until history continuation and rollback are verified.
6. Remove the legacy engine only in a separately reviewed change after production evidence confirms the migration gates.

## Known constraints

- The repository's current default Compose stack does not prove that an external Code API is installed or safely configured. Pi code execution remains unavailable until the deployment's Code API isolation and per-user authorization are verified.
- The upstream Pi SDK currently supports in-memory sessions, custom resources and custom tools, but its provider and event contracts differ from LibreChat's. Provider mapping and event translation are required; the SDK does not replace host authorization or durable job recovery.
- Performance and concurrency targets are relative to a measured deployment baseline. No absolute capacity claim is made before those measurements exist.
